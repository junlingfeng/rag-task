## 1. 现状与关键路径

已完成：需求分析、指标口径、架构与路线、追踪矩阵、风险清单、技术选型。
已完成度：**纸面 100%，代码 0%，语料 0%，数据 0%。**

这个 Case Study 的验收标准全部是量化指标，而量化指标依赖两样目前都不存在的东西：**能跑的服务**与**能打分的评测集**。因此关键路径是：

```
环境与骨架 ──► 真实延迟基线 ──┐
                              ├──► 三配置对比 ──► 问题诊断 ──► 报告
语料与评测集 ──────────────────┘
```

两条并行链，缺一条都无法交付。它们也是耗时最长的两条，必须最先启动。

**常见错误做法**：先花几天把检索、重排、缓存、日志全部写完，最后才发现没有评测集，指标一个都算不出来；或者发现本地 embedding 单条耗时 800ms，整套延迟预算全部作废。

## 2. 下一步：M0 的四件事

### T0 环境与 Walking Skeleton（最高优先级，约半天）

目标：**用最薄的链路打通"文档 → 检索 → 生成 → 日志"**，只为拿两个真实数字。

| 步骤 | 具体动作 | 产出 |
|---|---|---|
| 环境 | `uv python install 3.12` + 项目虚拟环境（系统 Python 3.8.2 不可用） | `.python-version`、`pyproject.toml` |
| 依赖 | Qdrant + Redis 用 Docker Compose 起单机 | `docker-compose.yml` |
| 最小链路 | 20 份文档入库 → 一个问题 → 带引用的回答 | `scripts/ingest.py`、`scripts/ask.py` |
| 打点 | 每个阶段一行 JSON 日志 | `logs/*.jsonl` |

**验收标准（必须拿到实测数字）**：

- 单条 query 的 embedding 耗时（决定 2.4 节的估算是否成立）
- 20 候选的重排耗时（决定是否必须降到 10 候选或换更小模型）
- 一次完整问答的端到端耗时分解

这三个数字**直接决定延迟预算能不能成立**，也决定 [TECH-STACK-SELECTION.md](TECH-STACK-SELECTION.md) 里的估算是保留还是推翻。在拿到它们之前，不要写第二行检索代码。

### T1 语料建设（并行启动，约 1 天）

需求文档没有提供任何语料，这是最大的一处真空。

| 问题 | 处理方式 |
|---|---|
| 有真实内部文档吗 | 首选真实文档；注意脱敏，且不要使用真实 PII |
| 没有怎么办 | 按四类（员工手册、合规指南、技术规范、架构文档）合成中英双语语料，含 2–3 份扫描件（图片型 PDF） |
| 规模 | 建议 30–60 份文档、5k–20k chunk，足够体现 hybrid 与重排的差异 |
| 必须造假的场景 | 扫描件必须有，否则 OCR 与"小部分扫描件"这条需求无法体现 |

产出：`data/corpus/raw/` 原始文档 + `data/corpus/processed/` 解析结果 + 一份语料清单（doc_id、语言、类型、是否扫描件、页数）。

### T2 评测集建设（并行启动，最关键，约 1.5 天）

按 [METRIC-DEFINITIONS.md](METRIC-DEFINITIONS.md) 的表构建六个子集：

| 子集 | 规模 | 关键字段 |
|---|---|---|
| 单轮可答 | ≥ 100 题 | question, gold_answer, gold_chunk_ids, lang |
| 多轮会话 | ≥ 20 组 | turns[], 依赖改写的追问 |
| 越界 | ≥ 30 题 | 语料无答案 |
| 不安全 | ≥ 20 题 | 注入、越权 |
| 低置信度 | ≥ 20 题 | 近似但无确切依据 |
| 双语/混排 | 均衡 | 中文问英文文档 |

**先做 20 题的最小可用版本**，用它校准指标脚本，再扩到全量。不要一次性标完 200 题才发现标注口径错了。

产出：`data/eval/*.jsonl` + `data/eval/README.md`（标注口径与版本）。

### T3 指标脚本空壳（约 1 天）

先实现计算框架，不追求 judge 精度：读评测集 → 调服务 → 调用 judge → 输出指标 → 生成 CSV。

**验收标准**：能在 20 题小集上跑出 Faithfulness 与 Context Precision 两个数字，哪怕数值还很难看。

## 4. 明确不要现在做的事

| 不要做 | 原因 |
|---|---|
| 先写缓存与语义缓存 | 缓存命中率是报告指标，但没有基线数据时无法判断缓存是否改善了什么 |
| 先做 PII 与注入检测 | 属于 M3，且依赖日志字段定型 |
| 先接入多个生成模型做对比 | 没有评测集，对比结果没有意义 |
| 先做前端 | 需求只要求 API |
| 先优化代码结构 | 问题诊断需要先有可观测的真实数据，重构留在 M6 之后 |
| 追求一次把指标做到 90% | 指标达标是结果，先让链路跑通并产出可信数字 |

## 6. 需要确认的一个决策

**语料从哪来？** 这个决策会改变 T1 的做法，但不阻塞 T0：

| 选项 | 影响 |
|---|---|
| A. 有真实内部文档可用 | 需要先脱敏；语料质量高，OCR 与双语场景真实 |
| B. 没有，需要合成 | 需自行生成四类中英双语语料并制作扫描件；可控性高，但需保证真实性 |
| C. 用公开数据集替代 | 最快，但双语与扫描件覆盖度需自行补齐 |

**默认假设：走 B**，先合成一份中英双语语料并自制扫描件，因为它完全不依赖外部条件，且能精确覆盖需求里的四类文档与扫描件场景。如果你手上有真实文档，告诉我，改成 A 会显著提升评测的可信度。

## 7. 立即可以开始的第一步

无论语料走哪个选项，T0 都可以现在开始，且它的产出（真实延迟数字）是后面一切的前置条件。
