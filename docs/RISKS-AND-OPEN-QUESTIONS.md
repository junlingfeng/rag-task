# 风险清单与待确认问题
> English version: [RISKS-AND-OPEN-QUESTIONS.en.md](RISKS-AND-OPEN-QUESTIONS.en.md)


## 一、风险清单

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 无现成语料与标注集 | 所有质量指标无法计算，项目无法交付 | 优先自建数据集（M0），规模不足时在报告中声明并说明抽样方法 |
| 自评闭环（生成与评判同模型） | 指标可信度被质疑 | 生成/评判模型分离；≥ 20% 人工复核并报告一致率 |
| 三配置对比不可比 | 结论无效 | 固定评测集、prompt、模型、top_n、种子；记录配置快照与版本号 |
| 需要"2 个问题诊断"但指标一次做绿 | NFR4 无法交付 | 主动设计并记录真实退化事件，保留修复前后数据 |
| 重排器拖高 P90 | 违反 10s 硬约束 | 超时降级、批量重排、缓存兜底，并实测 P90 |
| 中文分词质量差 | hybrid 退化为英文关键词匹配 | 使用成熟中文分词/多语言检索方案，并以双语子集验证 |
| OCR 质量低 | 扫描件相关内容永远检索不到 | OCR 质量抽样评估，必要时人工校正或标注为已知限制 |
| 日志含 PII | 安全合规风险 | 日志前置脱敏、哈希化，缓存键同样不落明文 |
| 缓存返回陈旧答案 | Compliance 下降 | TTL + 重新索引触发失效；监控"命中缓存请求"的 judge 分数 |
| 指标量纲混用（% 与 0–1） | 验收方误读 | 报告统一量纲并显式标注映射关系 |
| 延迟口径未声明 | P90 结论可被质疑 | 明确端到端边界（含/不含流式），并在报告中固化 |
| 评测与线上代码路径不一致 | 评测结果不代表线上 | 共用同一检索/生成代码路径，仅通过配置区分 |

## 二、需要向出题方确认的问题

1. 语料从哪里获取？是否提供样例文档？语料规模（文档数/页数/总 token）大概多少？
2. 端到端延迟的口径：是否为"完整响应返回"？是否允许流式输出？
3. "≥ 5 并发"的验收方式：并发模型、请求分布、持续时长、目标硬件规格？
4. 是否有模型与预算限制（是否允许调用外部 API，是否有 cost cap）？
5. 是否有指定的评测数据集，或完全由候选人自建？
6. Answer Compliance / Style Consistency 是否有官方定义，还是完全由候选人在报告中定义？
7. "2 个问题诊断"是否必须是真实发生的问题，还是允许设计受控实验制造回归？
8. 交付形式与时限：代码仓库、报告格式、是否需部署运行？
9. 是否需要前端或仅需 API？
10. 安全方面的深入程度：注入防御是"最小化即可"还是需覆盖具体攻击类型清单？

## 三、默认假设（若无法获得答复则按此推进）

| 项 | 默认假设 |
|---|---|
| 语料 | 自建基于公开文档 + 合成的企业内部资料，并自建标注集；规模在报告中声明 |
| 延迟口径 | 非流式，端到端 = 请求进入 → 完整响应返回 |
| 并发 | 单一实例，恒定 5 并发，混合请求分布，压测持续 ≥ 5 分钟 |
| 模型 | 允许调用外部 API，选用性价比模型作为主模型 + 一个大模型作 judge |
| 评测集 | 完全自建，划分固定并版本化 |
| 指标定义 | 采用 [METRIC-DEFINITIONS.md](METRIC-DEFINITIONS.md) 中的口径，并在报告中显式声明 |
| 问题诊断 | 通过受控实验制造真实回归，如实记录数据 |
| 交付形式 | 代码仓库 + 一键脚本 + Markdown/CSV 报告 |
| 前端 | 仅提供 API（含 curl 与最小 demo） |
| 安全深度 | 覆盖常见注入模式 + PII 脱敏 + 无据拒答，不追求完整攻防体系 |
